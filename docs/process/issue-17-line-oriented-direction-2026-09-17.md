自動対応の比較単位を行とする。最小編集距離の計算量への指摘を、行指向への変更指示の撤回やバイト比較への復帰として扱わない。

## 承認済み契約との関係

上位の Issue #17 R1 は、immutable な由来をバイト範囲で記録し、その同一性とコピー一致を検証することを要求する。一方、自動対応探索を全文 byte-token alignment とする方式は後続設計で具体化したものである。

今回変えるのは**変更前後の原文の対応を探す比較単位**。保存する原文 bytes、Seal content 上の由来範囲、source 範囲の byte offset と長さ、コピー一致検証は維持する。行で見つけた対応を、保存済み byte 範囲へ結び付ける。

次の旧契約は、そのまま今後の実装根拠に使わない。

| 対象 | 今回の指示と両立しない箇所／再具体化が必要な箇所 |
|---|---|
| ADR 0032 §5.2 | 全文バイト列の挿入・削除を自動比較の単位とする規定、バイナリ適用をその方式の理由にする説明 |
| ADR 0034 §2～§3 | byte-token の保持・挿入・削除、対象範囲への投影、byte格子の全サイズによる予算、旧比較例 |
| ADR 0035 §1/§3/§4 | `max-alignment-cells`、計数と停止条件、範囲結果の編集・保持情報、方式表示 |
| ENVIRONMENT_REVIEW 初回案 | byte格子の大きさを根拠にした実験入力・順序変更案。未承認の案であり採用しない |
| 実装計画 S3、S4、S6 の比較関連検証 | 行対応と byte 範囲への投影を基準に更新する |

ADR 0033 の保存形式、Cause Link の whole-Seal 対象、既存 STALE、自身・上流・下流の分離、意味論を監査しない方針、status の保留は変更しない。

旧 ADR と承認記録は履歴の exact bytes として保持する。旧契約全体の承認を取り消すものではなく、本指示に抵触する比較方式とその下流への適用を置き換える。詳細改訂では、本指示と両立する既存の曖昧性・明示宣言・構造検証要件も維持する。

## 詳細設計で具体化する境界

改行の区切り、改行 bytes の扱い、行途中から始まる抜粋の対応、編集された行の扱い、曖昧性、比較予算と出力の変更を[行指向比較の詳細候補](issue-17-line-oriented-comparison-candidate-2026-09-17.md)にまとめる。行指向の方針自体の再承認は求めず、新しく具体化した詳細を Proposed として区別する。

所有者がバイナリ比較の利用価値を疑問視したことから、未知の文字コード・特定拡張子・任意 byte 入力の拒否規則は追加しない。保存の exact byte 検証と、任意バイナリの編集対応探索を製品目的とすることを区別する。

## 計算量の説明訂正と影響範囲

全文格子の大きさ `(m+1)*(n+1)` は、全ての最小編集アルゴリズムが実際に処理する量ではない。最短の挿入・削除列を求める Myers 法は差分量に依存する O(ND) とされる（N は列長の合計、D は最小挿入・削除数）。今回要求する全最適対応の合意検査まで同じ計算量で実現できるとの証拠はまだない。

この区別をせずに全格子の大きさから byte比較の実用性を判断した先の説明は撤回する。行指向の選択は所有者の利用目的・指示に基づき、byte指向が常に二乗で不可能という主張を根拠にしない。

影響確認対象は ADR 0032/0034/0035、環境レビュー、実装計画の比較関連部分。製品の比較器は未実装なので、今回修正する対象は設計・計画である。性能値や製品完成はまだ確認していない。
