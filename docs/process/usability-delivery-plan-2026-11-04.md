## 工程と依存の理由

```text
FORMAT6_METADATA_READY
  → UX_REQUIREMENTS → UX_CONTRACT
  → UX_DESIGN_CONTRACT → UX_DESIGN
  → [日常点検 / 本文比較 / 原文監査 / 歴史版表示] → UX_RUNTIME
  → [ライトユーザ手順 / LLMガイド] → UX_GUIDED
  → UX_INTEGRATION_VERIFY → UX_VERIFIED
  → UX_PERSONA_REVIEW → UX_SCENARIOS
  → UX_OWNER_ACCEPTANCE → UX_READY
```

4つの表示機能は互いの成果を前提にせず、合意した設計だけに依存する。2つの案内は実装された操作との一致を必要とするため表示機能の後に置く。結合検証は表示と案内の両方を必要とする。独立操作レビューは検証済みの実物を必要とし、最終受入はその証拠を必要とする。並行可能な依存を単独実行資源で偽って直列の依存に置き換えない。

## 完了の意味と保留する判断

- UX_CONTRACT: 6件の対象、初回登録・変更発見・新版採用・旧版維持・保留・第三者監査の6場面、レビュー手順/閾値、通知の採否または保留範囲が所有者と確定している。
- UX_DESIGN: 正確な版の選択、原文取得、本文差分、未確認/失敗/不完全/バイナリ/サイズ上限、公開CLIと検証方法の対応が確認されている。契約変更は既存の要件/ADRの手続きに戻す。
- UX_RUNTIME: workfile相違・上流Seal stale・引用原文残存を別事実として示し、本文/原文/根拠版/判断理由へ辿れる。歴史版維持の判断と現在への適用可否をstaleと別軸で読める。
- UX_GUIDED: 初見利用者とLLMが、Candidateなしの開始状態から原文/版/差分/影響を読み、更新/維持/保留を選び、個別操作と読み戻しへ進める案内が実装と一致する。
- UX_VERIFIED: リポジトリ必須検査と設計に対応した結合/回帰検証を通し、未検証範囲を記録する。
- UX_SCENARIOS: 開発者の自己確認と独立レビューを区別し、3者6場面を合意した閾値で操作レビューした証拠が揃う。独立担当の確保は未了。
- UX_READY: 全6 Workと要件の完了証拠・残課題を提示し、所有者が成果の受入を判断した記録を持つ。受入はrelease/install/pushを許可しない。

通知は手動点検だけで要求を満たしたと扱わない。対象・契機・通知先の採択、または明示的保留と残る義務をUX_REQUIREMENTSで決める。自動Cause更新・自動Seal・Git自動検出は追加しない。意味的妥当性・承認・理解を構造整合や原文一致から自動認定しない。
