# SealGraph 利用者運用要件 R1

Status: Proposed / first-owner-review待ち。2026-11-04。Task: UX_REQUIREMENTS。
計画の採用・実装依頼とは別に、この要件本文は未承認。下記の通知範囲N1を含む具体的な契約として所有者に判断を求める。

## 1. 目的と現行根拠

ライトユーザ、LLM、監査者が、対象を登録し、変更の種類を区別し、原文と正確な根拠版を確認して、更新・歴史版維持・保留を選び、結果を読み戻せること。利用者がコマンド体系を暗記していることを前提にしない。

根拠は2026-11-04のユーザーによる3者の独立レビュー依頼、6改善Work、採用済みPLAN.pertのUX工程、計画採用/実装進行の指示。SealGraphの現行規範はdocs/requirements.md、docs/cli.md、docs/storage-format.md、docs/architecture.mdとAccepted ADRが所有する。特にADR0019のsource/baseline、ADR0022のhuman/JSON境界、ADR0036–0042のTrace、ADR0043のhistorical reviewを保持する。

計画の固定版Sealは `6718cbf73eee629090e9d53784355127fe4f7fc367a1adebff0cfe0e66613e0f`。これは実績記録開始前のPLAN.pertであり、製品要件の受入証拠ではない。

## 2. 契約と既存契約の扱い

### UX-R01: 入口と操作ナビゲーション

README、repository-local運用ガイド、CLIヘルプは初回登録・日常点検・根拠見直し・原文監査の入口を示す。利用者は入口から、対象REF/正確なSeal版/観測範囲/次の読取り操作を知ることができる。LLMには同じ入口を案内し、ユーザー専用のローカルSkillを必須にしない。

### UX-R02: 日常点検と通知範囲（採択提案N1）

N1: 今回は利用者または明示的に呼び出す実行者が点検を実行した時に、その出力で変更と見直し対象を知らせる。常駐watcher・定期実行の登録・OS通知・外部メッセージ送信はこの版の実装に含めない。

この提案では「利用者が操作していない間にも変化があれば通知される」という期待は満たさない。その期待を満たすには、N2（別途合意した対象/頻度/通知先へ読取り専用の定期通知）を要件化する必要がある。N1を採用するか、N2へ改訂するかは所有者の判断であり、手動点検を自動通知の代替として黙って納品しない。N2を選ぶ場合は新しい要件版と追加作業/常駐境界/検証を計画へ反映する。

N1の出力は、以下の3事実を混ぜずに示す。

1. 明示的source bindingを持つファイルとCandidateまたはHEAD内容の関係。
2. 保存されたCause/観測されたrevisionに由来するstale。
3. format7で明示的に結び付けた原文に引用バイトが残るかというTrace観測。

対象外、未登録、Traceなし、未束縛、読取失敗、不完全観測は「変更なし」に含めない。ファイル全体の同時snapshotや点検後の予約を主張しない。無指定で全ファイルを探索したりGitを検出したりしない。

### UX-R03: 原文を読んで見直す

対象の内容、Candidateの有無、依拠する各Causeの正確なSeal版、比較対象版、その差分、影響の確認先へ進める。Candidateなしからの準備を案内する。新版採用・歴史版維持・保留の3経路を区別する。比較対象が複数のactive leafなら勝手に最新1件へ絞らない。

新版採用は必要な個別Cause操作と個別Seal発行を担当者が判断する。歴史版維持は既存ADR0043の個別review経路を用いる。保留では未確認状態を保持し、clean化を完了条件にしない。案内はユーザー承認や意味的判断を生成しない。

### UX-R04: 本文の比較と完全な原本への到達

明示的に固定した2版の本文の違いを読める。本文だけでなくCauseの追加/除去/変更と判断理由の読取り先を区別する。human表示の省略・上限・バイナリ非表示を明示し、正確な全文原本へ到達する手段を案内する。

現行のbytes-only出力は保持する。既存のJSONスキーマ/exit code/デフォルト出力の意味を無断で変更しない。新しいCLI/出力を必要とする場合、その名前、サイズ/計算量上限、スキーマは基本設計で決め、Accepted契約と競合する部分を所有者へ戻す。既存human previewの256バイトだけを完全な本文レビューと称しない。

### UX-R05: 原文監査

特定Sealの記述・保存された正確なCause版・保存原文・引用範囲と前後文脈・比較差分・記録された判断理由を読み取り専用で照合できる。原文の現在ファイルと保存Snapshotを混同しない。

Candidate/HEAD、snapshot/current、1代表位置/全出現位置、ページ途中/完了、未確認/観測失敗を明示する。現行Traceの存在比較・推定・occurrence listingの意味を変更しない。Traceのない過去版へ原文来歴を自動で補わない。

構造整合、引用バイトの一致、主張を原文が意味的に支えるかは別の確認である。最後は監査者が原文を読んで判断する。fsck成功、Seal、一致位置、review claimの存在を意味的正しさ・承認・理解の証明として表示しない。

### UX-R06: 歴史版維持の見え方

staleをそのまま示し、別の欄で記録された判断、現在観測への適用可否、未確認範囲、失効理由の確認先を案内する。全other-head観測に基づく既存の失効条件を緩めない。過去判断が存在するが現在は適用不可、という状態を表示可能にする。

### UX-R07: 人とLLMで共通の操作規律

読取り専用の列挙/差分/確認資料作成と、対象ごとの判断・Cause更新・Seal発行を分ける。自動Cause更新・自動発行・再試行によるclean化は提供しない。1操作1 REF、immutable objects、standaloneのGit非検出、明示的root、exact Cause、draft/歴史版の区別を維持する。

## 3. 観測可能な受入シナリオ案

共通条件: coreはformat5/6/7、Traceはformat7のみ。safe temporary fixtureを用い、原本・選択版・変更内容・期待事実を事前に固定する。暗記や外部の開発者用資料を前提にしない。独立レビュー担当は作者と別の主体とする。初見の実利用者試験とLLMによる役割試験を区別して報告し、片方を他方の証明にしない。

| ID | 場面 | 合格条件案 |
| --- | --- | --- |
| S1 | 初回登録 | 入口から前提と依存する内容を登録し、rootの意味と根拠の特定版を説明でき、担当者の個別判断後に読み戻せる |
| S2 | 変更発見 | ファイルだけの変更、上流Seal更新、引用原文の移動/不一致を区別し、未束縛・読取失敗・Traceなしを変更なしと取り違えない |
| S3 | 新版採用 | Candidateなしの開始状態から、対象/旧根拠/比較版原文を読み、差分と影響を記録し、個別更新後のexact Causeを確認できる |
| S4 | 旧版維持 | 旧版根拠と比較対象を読み、ADR0043の記録を扱い、staleが残ることと現在適用可否を区別できる |
| S5 | 保留 | 原文/影響の未確認を保留し、更新/発行せずに未完了を報告できる |
| S6 | 第三者監査 | 保存対象/根拠/原文と文脈/記録された理由を照合し、構造検査で確認済みの範囲と意味的未確認を別に結論づける |

各場面で、入口資料から必要な操作を選び、原本とexact IDを示し、上記の区別を誤らずに完了または正しく保留できることを必須とする。作者がコマンドを教えなければ進めない点、出力を誤読した点、証拠が足りない点は記録し、修正/再レビューの対象とする。所要時間・クリック数の合格閾値は今回は置かず、観測値として記録する。

本文比較には256バイトより後だけが変わる4KiBテキスト、本文/原文の省略確認には2MiB fixture、バイナリにはNUL/CRLFを含むfixtureを使う。引用には複数出現、移動、消失、対応先未束縛、ページ途中のfixtureを含める。これは確認場面の最低入力であり、無制限表示や任意サイズの性能保証ではない。安全な読取り/上限/競合時の挙動は設計と試験で具体化する。

検証にはgofmt、go vet、go test、npm ci、clone-check、complexity-check、deadcode-checkを含める。既存仕様と公開JSONの回帰、読取りがcanonical/Candidateを変更しないこと、原文読取りが明示対象に限定されることを確認する。

## 4. 要件版と後続フェーズ

このR1は提案で、normative docsやAccepted ADRをまだ置き換えない。所有者の最初の確認、指定ルートによる独立レビュー、変更していない版への2回目の所有者判断を経てからAcceptedへ進む。本文変更時はR2として出し直す。

設計フェーズが所有するもの: CLIの具体的綴り、モジュール分割、内部API、表示上限/アルゴリズム、JSON新規スキーマ、観測一貫性と再検証の実装。既存契約への影響が判明した場合はその所有フェーズへ戻す。

不明点: N1で利用者の通知期待を満たすと所有者が判断するか、N2が必要か。独立レビュー担当と実利用者試験の確保時期。これらを実装済みや検証済みと扱わない。
