# Issue #17 要件候補：小さな Seal のための範囲 Trace と方向別の差異観測

- 日付：2026-09-17
- 文書版：R1（会話内の草案を再修正した、最初のファイル保存版）
- 状態：要件候補。文書全体の承認前。設計・実装の完了を意味しない。
- 言語：日本語を本候補の本文とする。
- 対象：Seal の対象コンテンツの由来を範囲で記録し、自身・上流側・下流側のファイル差異を観測する機能。
- 関連 Issue：[Issue #17](https://github.com/mako10k/sealgraph/issues/17)
- 既存仕様の照合基準：main `c23aa34`。

## 1. 目的と期待する利用結果

Seal を小さく扱えるようにしながら、既存の大きな文書との対応を保つ。
利用者は、大きな元文書を物理的に細分化せず、必要な範囲から小さな Seal を作成できる。
複数の元文書の一部と Seal 独自の表現を組み合わせる場合も、その対応を表せる。

元文書を改訂した際には、Trace を手掛かりに関係する範囲を追い、どの Seal の自身・上流側・下流側に差異があるかを確認できる。
周辺の編集、複製、移動などで対応が曖昧になる場合があるため、改訂後の対応の完全な復元は保証しない。

「Seal を atomic にしたい」という意図は、元文書の大きさに拘束されず小さな内容単位を扱う目的として保持する。
数値的な最大サイズ、意味上の最小単位、内容が atomic かを自動判定する規則は、この会話では定められていない。

本候補の成果は要件判断の材料である。機能として利用できる時期は、残る要件判断、設計、実装、検証、提供を経た後であり、日付は未定。

### 2.2 既存文書との関係

- [現行要件](../requirements.md) §2.3～2.4 の immutable Seal と exact whole-Seal Cause Link、および §3 の STALE 定義を維持する。
- 現行要件 §14.1 と [ADR 0019](../adr/0019-local-file-tracking-and-implicit-add.md) の binding は、ローカルファイルの入力選択である。現在のファイルと Candidate／HEAD の差異を示す `WORKFILE_DIFFERS_FROM_*` は、STALE と別に扱われる。
- [ADR 0024](../adr/0024-source-adapters-and-portable-occurrence-provenance.md) は、ローカル binding と永続的な出所記録を区別している。範囲 Trace の配置は未決であり、binding をそのまま canonical provenance に転用すると決めない。
- [ADR 0025](../adr/0025-universal-blob-seal-material-and-provenance.md) の immutable Blob、Material、Provenance、Seal の境界を設計の照合対象とする。
- [ADR 0028](../adr/0028-upstream-impact-assessment.md) の上流影響・Assessment は既存の承認済み設計である。本候補では上流側と下流側を区別する。binding／Trace 差異に Assessment の記録義務や公開ゲートを追加する判断は行っていない。
- Issue #17 の当初案にある「断片を Cause の対象にする」「断片の存続から直接 STALE を導出する」という読み方は、U1 に従い本候補では採用しない。

既存の規範文書、保存形式、公開 CLI 契約は本候補の作成だけでは改訂されない。保存形式などに変更が必要であれば、後続の設計で対象となる既存の決定と変更内容を明示する。

## 3. 範囲 Trace

R1. Seal の対象コンテンツについて、バイト範囲ごとの由来を記録できること。
ここで扱うバイト位置は対象コンテンツ内の位置であり、Seal の管理レコードをシリアライズしたバイト列の位置ではない。

R2. 一つの対象コンテンツ内で、複数の元ファイルの範囲と、Seal 独自の表現を混在させられること。元ファイルを物理的に分割することを前提にしない。

例として、60 バイトのコンテンツを次のように対応付ける。範囲は 0 始まりの半開区間とする。これは説明用表記であり、保存形式や CLI の構文を決定するものではない。

| 対象コンテンツ内の範囲 | 記録する由来 |
|---|---|
| `[0, 20)` | ファイル A の特定の版の `[100, 120)` |
| `[20, 30)` | Seal 独自の表現。外部範囲への対応なし |
| `[30, 60)` | ファイル B の特定の版の `[5, 35)` |

R3. 外部由来の範囲について、元の版、範囲、対象バイト列との一致を検証可能にすること。可変なファイル名と位置だけで過去の由来を表したことにはしない。版を識別する形式や元データの保持方法は未決とする。

R4. 外部範囲への対応がない部分を明示できること。この記録は、現実世界に由来や根拠が存在しないという主張にはしない。

R5. 元ファイルが後から変わっても、記録済みの過去の Trace を書き換えない。過去の由来と現在のファイルとの比較結果を区別する。

Issue #17 の Origin Run の長さ、連続する run の統合、空コンテンツ、全バイトの被覆などは設計の入力として残す。正規形式、検証規則、保存場所は後続の設計で確定する。

## 4. 中間 Seal と Cause Link

R6. 原文から必要な範囲を抜き出した小さな中間 Seal を作り、別の Seal がその中間 Seal 全体を Cause として参照できること。

```text
言い換えを含む Seal D ──Cause──> 抜粋を収めた Seal E
                                  │
                                  └─Trace─> 大きな元文書の特定の範囲
```

E は原文とのバイト対応を記録する。D は E の正確な Seal 世代への依存を記録する。
D の言い換えを原文からのバイト単位のコピーとして扱う必要はない。
Cause の参照先を E 内の一部分へ変更しない。Sealgraph は D の内容や D→E の意味上の妥当性を監査しない。

## 5. 自身の Trace 比較

R7. 元ファイルの現在の観測と、選択した比較基準に記録された Trace とを照合し、対象範囲ごとの結果を示すこと。
REF の自身の比較では、現行 source compare と同様に Candidate があればそれを、なければ HEAD を比較基準とする案とする。
比較結果には、使用した基準と元ファイルの観測を識別できる情報を持たせる。

| 仮称 | 判定内容 |
|---|---|
| `MATCHES` | 現在のファイルで対応範囲を特定でき、そのバイト列が基準と一致する。 |
| `DIFFERS` | 対応範囲の内容変更、または削除を確認できた。 |
| `UNRESOLVED` | 対応が曖昧、必要なファイルを読めないなどの理由で比較を確定できない。 |

R8. 対応を特定できて内容が一致する場合、位置だけの移動は `DIFFERS` としない。位置の変化は別に示せること。
元ファイル全体の版が変わっていても、Trace 対象の範囲については一致という結果を持てること。

R9. 文字列検索の失敗だけで削除と断定しない。同じバイト列が存在するだけで由来の対応が確定したとも扱わない。
対応付けに使う方法と根拠を定め、確定できない場合は `UNRESOLVED` とする。具体的なアルゴリズムは未決である。

R10. Seal 独自表現の範囲は外部範囲との比較対象を持たない。Trace がない、比較対象がない、未調査、比較して一致した、というケースを同一視しない。

これらはコンテンツの意味の比較ではない。周囲の文章によって読み方が変わっても、意味論による追加判定は行わない。

## 6. 自身・上流側・下流側の独立した状態

R11. 次の 3 区分を独立した観測として保持・表示すること。

| 区分 | 対象 |
|---|---|
| 自身 | 観測対象の Seal 自身の Trace 比較結果 |
| 上流側 | 観測対象が Cause をたどって依存する Seal の Trace 比較結果 |
| 下流側 | 観測対象を直接または間接に Cause として参照する Seal の Trace 比較結果 |

R12. 各区分では「差異あり」と「判定不能あり」が併存できること。
一方を表示するために他方を消さない。比較・調査の範囲と未調査部分を識別できること。
対象がないことや未調査であることを、確認済みの一致として表示しない。

R13. 上流側・下流側の結果では、該当する正確な Seal 世代、Trace 範囲、比較結果と理由、Cause の経路を確認できること。直接・間接を区別すること。
同じ Seal に直接の経路と間接の経路がある場合の表示方法、経路数の制限は設計で定める。

R14. 各区分は、各 Seal 自身で得られた比較結果を、その区分の方向の Cause 経路に沿って集計する。
既に集計した「上流側に差異あり」を逆方向へ流して、新しい「下流側の差異」の発生源にしない。方向の混在や集計結果の往復を避ける。

例では、矢印を「依存する」の向きとする。

```text
C ──Cause──> B ──Cause──> A
```

| 差異が観測された Trace | A から見た状態 | B から見た状態 | C から見た状態 |
|---|---|---|---|
| A 自身 | 自身に差異あり | 上流側・直接に差異あり | 上流側・間接に差異あり |
| B 自身 | 下流側・直接に差異あり | 自身に差異あり | 上流側・直接に差異あり |
| C 自身 | 下流側・間接に差異あり | 下流側・直接に差異あり | 自身に差異あり |

判定不能についても同じ位置関係で示す。
例えば A の Trace が差異あり、C の Trace が判定不能なら、B は「上流側に差異あり」と「下流側に判定不能あり」を同時に持てる。

R15. 関係の判定では Cause Link が保持する正確な SealID を使う。
依存先の REF が進んでいても、新しい HEAD や Candidate を、Cause が実際に指す世代の代わりに比較しない。
REF 自身の Candidate 優先比較と、immutable Seal 間のグラフ観測の対象を明示する。
未公開 Candidate の Cause を方向別の集計に含めるかは未決とし、既存の Seal グラフへ暗黙に混ぜない。

R16. 特に下流側は、観測したリポジトリ／グラフの範囲を明示する。
観測範囲外の依存者まで存在しないと主張しない。範囲の既定値、履歴を含むか、読み取り中の変化の扱いは設計で定める。

## 7. STALE と構造監査の境界

R17. ファイル側の差異や Trace の判定不能だけを理由として、Seal を STALE にしない。
既存の `STALE_REVISION`、`STALE_DIRECT`、`STALE_TRANSITIVE` は既存の条件から導出する。
Trace の方向別観測と STALE は併記でき、片方の結果から他方を自動的に決めない。

既存 STALE の `DIRECT` 優先で `TRANSITIVE` の列挙を抑制する規則を、本候補の方向別差異集計へ暗黙に持ち込まない。
本候補では、自身・上流側・下流側の独立性と、差異・判定不能の併存を要件候補として明示する。

R18. 構造的な検証として、参照対象の存在・同一性、バイト範囲、宣言されたコピー対応のバイト一致、採用する形式の整合性、既存グラフの禁止された循環などを確認する。
履歴 Trace 自体の範囲外参照やバイト不一致は、現在のファイルが変わったという比較結果とは区別して扱う。

R19. 「赤と青を同義とする」「コンテンツの記述が矛盾する」「Cause に意味がない」といった内容の意味論を監査しない。
中間 Seal や Assessment が存在しても、意味論監査を追加の要件にしない。

## 9. 未決事項と採用していない追加案

1. Trace の保存場所、識別子、正規形式、元ファイルの版の固定方法と保持方法。
2. 改訂後の範囲対応を特定する方法、曖昧さ・複製・分割・結合の扱い、比較結果の理由の表現。
3. 範囲表現、全バイト被覆、連続範囲の統合、空コンテンツの扱い。
4. 観測範囲、Candidate と Seal の表示関係、下流の探索範囲、経路の表示制限、読み取り中の変更の扱い。
5. 公開 CLI、JSON schema、具体的な状態名。本文の英字状態名は仮称であり、既存の公開名前空間を再定義しない。
6. 既存の Trace なしデータ、過去の SealID、形式の版、互換性、移行の扱い。
7. 対象データと規模、性能・資源上限。測定条件や数値基準は未設定。

binding／Trace 差異を ADR 0028 の Assessment 対象に拡張すること、Assessment を必須にすること、公開ゲートを追加することは、本候補には含めない。
元ファイルの変更に伴う自動 Seal 作成、自動 Cause 書き換え、自動改訂関係の生成も本候補の要件ではない。
Issue #16 の Revision hyperedge、意味論監査、原文の物理的な分割、Seal 内容の意味上の最小単位の自動認定は対象外とする。
